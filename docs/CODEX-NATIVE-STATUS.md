# ECC: проверенное развёртывание в облаке Codex

Срез: **15 октября 2026 года**. Официальный native plugin ECC установлен
в отдельном постоянном контейнере в существующем облачном окружении.
Cloud-навык и native CLI используют общие исходные workflows, но остаются
двумя разными исполнителями. Защищённый профиль основной сессии не изменён.

## Как пользоваться

Практическая карта возможностей и порядок сопровождения:
[ECC-OPERATIONS.md](ECC-OPERATIONS.md).

В новой задаче выбрать **ECC Cloud**, прикрепить нужный проект и описать результат:
«Исправь issue … и проверь результат». Агент читает правила проекта, выбирает
подходящий ECC workflow и использует доступные инструменты. История этой беседы
для выбора правил и workflows не нужна.

Для native hooks, браузера и памяти агент проверяет существующий `ecc-native`
по [рецепту запуска](../plugins/ecc-cloud/runtime/README.md). Новая беседа не
требует переустановки или повторного входа при сохранённом рабочем профиле.
Новая виртуальная машина требует восстановления: автоматический перенос Docker
volume между разными облачными машинами не обещается.

**Реальный запуск подтверждён:** после официального device login модель
GPT-6-Astra / Ultra завершила инженерную задачу с двумя явно выбранными native
skills, независимым reviewer, тестами, coverage и ECC Memory MCP. Это результат
выполнения задачи, а не только `login status`. Пароли, токены, auth-файлы и
одноразовые коды в репозиторий не сохраняются.

**Постоянный режим согласования включён с явного разрешения владельца.**
В native-профиле сохранены только три параметра: `sandbox_mode=workspace-write`,
`approval_policy=on-request`, `approvals_reviewer=auto_review`. Штатный
`config/batchWrite` проверил версию файла перед записью; обратное чтение подтвердило
значения и сохранность остальных настроек. Новый обычный `codex exec` без
разового `--approve-for-me` выполнил команду после автоматического рассмотрения.

Первоначальный отказ автоматической проверки относился к отсутствию отдельного
разрешения на будущие запуски. Владелец затем явно согласовал эти настройки;
решение и проверка сохранены в [#12](https://github.com/alexpostnik/ECC/issues/12).
Вложенный `bwrap` по-прежнему не может создавать user namespaces. При таком
сбое запрос на конкретную команду рассматривает автоматический reviewer.
Защита контейнера, ядро и профиль основной облачной сессии не изменялись.

## Изоляция и границы

Native home находится в `ecc-native-home`; проект подключён отдельным bind mount.
Браузер — отдельный контейнер без agent profile, авторизации и проекта. Он работает
от `node`, с read-only root, `cap_drop: ALL`, `no-new-privileges`, без host ports.
На этом ядре Chromium user namespaces недоступны. Его `--no-sandbox` ограничен
browser-only контейнером; Docker isolation и сетевые ограничения хоста сохранены.
CA импортируется в временный NSS database. Память проекта остаётся приватной.

Это поверхность ECC, поддерживаемая Codex. Установленный native hook — SessionStart;
события Claude Code не становятся событиями Codex. Опциональные внешние сервисы
подключаются под конкретную задачу и с их собственной авторизацией.

Выполнение команды после одобрения через auto-review не означает, что вложенная
песочница `bwrap` заработала: её ограничение остаётся. Не следует отключать
изоляцию контейнера или менять системные параметры ради обхода этого ограничения.
Модели проектных ролей задаются их конфигурацией; например reviewer использует
свой модельный профиль. Настройка роли сама по себе не является доказательством
отдельной файловой изоляции.
Codex также предупреждает, что устаревший проектный ключ `persistent_instructions`
игнорируется. Маршрут правил обеспечивают проверенные `AGENTS.md`; этот ключ
не считается работающей настройкой и не мешал завершению проверочных запусков.

## Ошибки, обновления и участие

- [#9](https://github.com/alexpostnik/ECC/pull/9): узкий исправленный дефект
  проверки hooks, RED/GREEN и 56 тестов, независимое ревью. Это draft в нашем
  форке; принятие upstream не заявляется. На head `440766bc` GitHub показывает
  39 успешных и 4 неуспешных проверки: Windows storage assertion, две установки
  npm-зависимостей и Windows packed lifecycle. Причины последних трёх пока
  не установлены; успешная ограниченная приёмка не заменяет полный CI.
- [#10](https://github.com/alexpostnik/ECC/issues/10): native prompt catalog
  в первоначальном замере показывал 314 из 348 установленных ECC skills.
  Последующие CLI-процессы сообщили о 68 и 136 пропущенных skills соответственно;
  их состав отдельно не подсчитан, и числа не приписываются только ECC.
  Пропущенные навыки доступны
  через явный выбор по полному `skills/list`, в том числе TDD и verification-loop.
  Их реальное чтение и применение теперь подтверждены модельным запуском.
  Это проверенный способ выбора навыков, а не устранение лимита каталога.
- [#8](https://github.com/alexpostnik/ECC/pull/8): объединён в `main` коммитом
  `6e44d317b06e10fb1dad23020311726a9d48e5b4`. Все 45 проверок коммита
  `d50cf128` успешны, включая 43 jobs основного CI и Linux full suite 8799/8799.
  Повторный Windows Node 22/Yarn job завершился успешно; исходный локальный
  full-suite failure в managed cloud остаётся отдельно в #7.
- [#2](https://github.com/alexpostnik/ECC/issues/2): нестабильность Cloud skill
  discovery остаётся отдельной проблемой платформенного контекста. Native install
  проверен независимо; успех native не закрывает эту issue автоматически.

Для обслуживания достаточно поручить агенту «обнови ECC и проверь совместимость».
Агент сравнивает upstream, готовит отдельную ветку, проверяет изменения, обновляет
тот же приватный Cloud-плагин и отдельно native pin/image, затем повторяет приёмку.
Автообновления во время работы не включены. Ошибки приложения идут в его issues,
ошибки ECC — в форк ECC с воспроизведением; общий исправленный дефект готовится
отдельным небольшим PR для сообщества.
